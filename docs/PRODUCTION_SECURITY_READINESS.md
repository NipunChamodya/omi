# OMI production security readiness

Assessment date: 2026-10-27. Reviewed baseline: `6cf52c6`, plus the small remediation described below. **Release status: NOT READY for public deployment.** The implementation is suitable for continued controlled testing, but production transport, provider, secret-rotation and operational requirements lack current deployment evidence. This assessment does not declare the application completely secure.

## Scope and evidence rules

Reviewed actual server, engine, shared protocol, browser, persistence and infrastructure code, beginning with `SECURITY.md`, `SECURITY_REVIEW.md`, `SECURITY_COVERAGE_MATRIX.md` and `RED_TEAM_SECURITY_REPORT.md`. Historical reports supply context; their test totals and external-configuration claims are not treated as fresh verification.

The initial working tree was clean. No commit, push, merge, deployment, public tunnel, external attack or production-data mutation was performed. Tests used synthetic identities, loopback providers, mock storage, in-memory SQLite or disposable database files. Real `.env` contents and live database rows were not inspected; only the environment file's permissions were checked (0600). Advisory queries to npm were read-only and authorized. No production readiness CLI was run against the real database.

In the checklist, **Verified locally** means source enforcement and relevant automated assertions passed; **Reviewed** means source evidence with limited direct assertions; **Unverified** means deployment evidence is still required. A passed fixture does not establish Internet-scale resistance or validate the production service.

## Previous sensitive-broadcast finding

**OMI-RT-001 (previously Medium): fixed in the reviewed baseline; regression verification passed.** The earlier implementation allowed silent expired/revoked recipients to receive new room data before heartbeat cleanup. This assessment did not remove the existing fix or replay vulnerable code against real services.

- `multiplayer/rooms.ts::send` returns before serialization/transport send when the canonical identity is inactive and closes with 1008. Broadcast recipients come from the room peer map; actions and replacement connections have additional queue/current-peer checks.
- `voice/service.ts::send` and `social/service.ts::send` authorize the retained server-derived room ID and identity before transport delivery. Their route authorizers require room membership and the current open game socket with the same session hash. Authorization failure closes with 1008 and returns; the broadcast loop can continue for other recipients.
- `multiplayer/multiplayer.test.ts`, test **“does not deliver private deals to silent expired sockets between heartbeats”**, uses four real local clients and an injected clock. It asserts zero new messages to the silent expired player, close 1008 and the correct deal to the authorized cutter.
- `multiplayer/delivery-security.test.ts` separately revokes synthetic voice/social recipients, asserts zero sends to the revoked socket and confirms delivery to the authorized peer. These service spies test egress behavior; real route/session glue is additionally covered by the account/voice/social suites.
- These regressions passed in both the initial 159-test baseline run and the final 162-test run. No renewed bypass was demonstrated. Already received data and established malicious P2P media cannot be recalled.

## Confirmed defect and defensive fix in this assessment

**OMI-PR-001 — Low: environment-file inspection errors silently waive a readiness control. Fixed.**

Location: `apps/server/src/ops/preflight.ts::deploymentChecks`.

Expected behavior: an optional `.env` may be absent when configuration is injected, but permission/I/O errors must fail the file-inspection requirement. Previously the blanket catch omitted the check for every filesystem error. Under otherwise passing configuration, EACCES/EIO could therefore be ignored and readiness could report success without checking the credential file. This is an assurance failure; no remote file disclosure or account bypass was demonstrated.

Remediation: catch the error and record `private-env-file-if-present` as passing only for ENOENT; other errors record false. Existing present-file type/symlink/permission checks remain intact. This does not inspect or alter secret contents or add a runtime permission prompt.

Regression: three synthetic filesystem cases in `apps/server/src/ops/ops.test.ts`. Before the fix, EACCES and EIO failed their expected-false assertions because the check was absent; ENOENT passed. After the fix all three pass, with all 162 tests passing. An initial attempt to spy directly on the immutable ESM namespace failed in the test harness; a module mock corrected the harness before the pre-fix reproduction. No production filesystem permissions were changed.

Changed tracked source files: `ops/preflight.ts` and `ops/ops.test.ts`. No new dependency, gameplay rule or authentication behavior was introduced. No additional exploitable implementation defect was confirmed in the reviewed paths; that is a scoped finding, not evidence of complete vulnerability absence.

## Remaining risks and unverified requirements

1. **Production transport and topology:** no external TLS/certificate/cipher check, public port inventory, edge limits or deployed proxy-chain test. The checked NGINX template binds HTTP loopback and assumes a trusted edge/connector. Local processes share its trust boundary. Do not expose Vite, test providers, backend, SQLite, source tree or backups publicly.
2. **Identity/secrets:** real Google redirect registration, consent settings and callback acceptance are unverified. Earlier documentation records an exposed Google credential and a redirect mismatch; those are historical findings, not freshly confirmed external state. Obtain evidence of credential revocation/rotation and successful synthetic-account staging login before release. No historical Git secret scan was performed.
3. **Storage:** actual S3 IAM/public-access block, encryption, recovery and malicious-provider behavior unverified. Public sanitized avatar endpoints intentionally expose active avatars; profile display names/actor IDs are room-visible. Approve this privacy model. SQLite uses ordinary plaintext storage; protect disk/backups and temporary OAuth secrets with host access controls and encryption policy.
4. **Filesystem:** repository chmods the main DB and creates new private directories, but does not validate all existing ancestors or reject database-path symlinks before opening. Preflight checks the main file, not all ACLs/parents/WAL/SHM. Verify dedicated service ownership, private ancestors and umask 077 on the target; local path races were not exhaustively tested. No live data was used to test these conditions.
5. **Voice:** direct ICE can expose peer network addresses. Choose/approve relay-only policy if required; verify TURN TLS, denied private/multicast targets, allocation/bandwidth quotas and cost controls. One-hour credentials remain usable until expiry and are not room ACLs. Server logout stops signaling and supported-client capture, not already established malicious peer traffic. Specialized voice/relay and physical microphone/device suites were not rerun here.
6. **Abuse/availability:** per-IP fixed windows and bounded maps help but do not prevent distributed abuse, many legitimate-account creation, connection churn or edge-level slow clients. Finite global capacity can be exhausted. No sustained/adversarial 100-room capacity test or crash campaign was performed. Define service-level budgets and edge defenses before launch.
7. **Lifecycle:** single-process memory owns rooms, hands, scores and receipts; restarts lose games. No multi-replica session-cache invalidation, durable room recovery, account-wide revocation UI or server ban system is implemented. Do not scale replicas without revisiting these boundaries. A present connection can keep a room alive; the 512/member receipt budget eventually rejects further actions, including failed unique requests. Product lifecycle/abandoned-room handling needs explicit acceptance.
8. **Operational recovery:** live host hardening, service installation/reboot, alert delivery, private log rotation, encrypted off-device backup, coordinated avatar/database recovery and recovery objectives remain unverified. `/health` deliberately does not prove dependency availability or release readiness.
9. **Browser coverage:** the standard browser suite is Chromium; installed PWA, specialized social/themes, device/iOS/Safari and public network lifecycle tests need their own evidence. Do not infer real media or installed-app behavior from jsdom tests.
10. **Rules:** `RoomService` defaults policies to `{}` and the production entry point injects no owner rules. Accusation/no-trump/restart and ordinary next-round paths intentionally return `UNRESOLVED_RULE` when their required policy is absent. Test-only explicit policies are not production behavior. Resolve these product/game-integrity gates without inventing scoring or penalty rules.

## Production blockers and remediation priorities

**P0 — before any public release:**

- Activate and verify a currently patched supported runtime in the actual service; the shell's 22.13.1 is below the enforced baseline. Recheck runtime advisories independently of npm.
- Produce a passing reviewed production configuration gate for the intended same-origin deployment, followed by authorized staging verification of HTTPS/WSS, cookie flags, proxy trust/forwarding, private-file denial and exposed ports. A green preflight alone is insufficient; it is not automatically enforced by the production entry point.
- Confirm historical credential rotation, final Google registration/callback, production guest prohibition and successful synthetic-account login/logout/revocation.
- Verify private SQLite/backup filesystem ownership, storage IAM, encryption/recovery, service supervision and actionable monitoring. Approve voice privacy/TURN quotas if voice ships.
- Resolve owner-dependent rules or explicitly define a release scope that excludes unresolved workflows; ordinary next-round progression currently lacks a production policy.

**P1 — before final release review:** retain and review the remediation diff; run recipient regressions in CI; finish specialized voice/relay/PWA/device tests and a longer representative staging load test; perform an encrypted disposable restore drill; obtain independent review of authentication and real-time recipient authorization. This report and its fixtures were reviewed by the same agent, not a separately staffed security team.

**P2 — subsequent hardening:** improve account-wide session/revocation controls, abandoned-room lifecycle and moderation, automate advisory/secret scanning and operational alerts, and design shared revocation/durable state before any horizontal scaling.

The current decision is **NOT READY** because required deployment evidence and explicit product policies are outstanding, not because the previous broadcast fix failed. After the P0 gates are evidenced, reassess for **READY FOR FURTHER TESTING**; reserve **READY FOR FINAL RELEASE REVIEW** for completed staging, device, operational and independent review evidence.
